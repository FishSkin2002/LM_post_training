## 已核实的代码事实

- 实际评测文件名为 `evaluate_checkpoint.py`。
- 可执行训练入口只有 `train_sft.py` 和 `train_post_sft.py`。`training_workflow.py` 是共用模块，没有 CLI；DPO 与 GRPO 已共用后一个入口。
- 评测从 `sample_checkpoint.py` 间接导入 `generate_answers`，函数本体在 `generation.py`。它不调用随机抽题或单条生成包装；删除抽样入口前可改成直接依赖生成模块。测试也有抽样模块的引用，需要随实现调整。
- 当前评测生成每题后做一级判定并保存，全部完成后输出 JSON。独立重评沿用一级结果，逐题做二级及必要的三级，没有三级各自独立的进度。
- 生成按 JSONL 已保存条数定位；独立重评按题目 `index` 恢复已保存判决。`index` 是固定验证题序中的数据集索引，数值不连续，不能以 `max(index) + 1` 推算下一题。
- 现有二级要求 R1 与模型正式回答各有一个完整可解析的 boxed；截断题一级直接判错。三级无有效结果时保存待复核，普通续跑跳过，只有显式重试才处理。
- 当前缺少 API 密钥也会保存为待复核；若保留这一行为，补齐密钥后的普通续跑仍会跳过这些题。
- 各训练阶段结束后都会调用统一评测；整合三级会影响训练结束时是否自动调用 API。
- 现有需求明确要求生成与 API 独立。确认新的流程后，需要同步修订 `docs/training-workflow.md`、`docs/evaluation-rescoring.md` 等要求，再经独立 PR 合入；之后从最新远程 main 开始功能实现。

## 第一轮待决问题

1. 目录与训练命令：建议根部只留 `train.py` 和 `evaluate_checkpoint.py` 两个业务入口；其余根部业务脚本放入 `post_training/`，命令为 `python train.py sft|dpo|grpo ...`。现有 `tools/` 与独立旧依赖区 `legacy/` 保持职责。
2. 级别与执行顺序：建议全量完成生成及一级，再完成二级，最后统一执行三级；而不是每题立即串联三级。各阶段独立恢复进度。
3. 训练结束自动评测：是否也默认走完整三级；建议与手动评测使用同一流程。
4. 已有评测复用：建议统一入口保留 `--input`，可对已有完整评测 JSON 沿用一级结果继续后续判定，不重新加载模型生成。
5. 三级缺密钥：建议进入三级前明确报错并保留前两级进度，不把尚未发出请求的题记为已处理；真正请求后仍无有效判决的题保留现有待复核语义。
